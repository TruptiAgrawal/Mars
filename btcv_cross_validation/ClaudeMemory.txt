KEY TECHNICAL DISCOVERIES (why the plan looks the way it does)
-----------------------------------------------------------------
1. Train/test split for BTCV is baked in at CACHING time, not training time.
   The main repo's cached_dataset2/01_BCV-Abdomen/ only ever contained the
   24 "train" volumes -- the 6 "test" volumes (35-40) were never cached
   there. Confirmed by reading meta .npy files directly.
2. `datasets/cache_dataset3d_e2.py` (used by the live job) hardcodes the
   filenames "01_BTCV_train_4to1.txt" and "WORD_50_train.txt" inside
   data_txt_path, ignoring whatever `dataset_list` is set in the yaml
   config. It also unconditionally mixes in WORD-50 data. This is why a
   dedicated CV-only loader was needed instead of just changing yaml keys.
3. Only `core/learner_sub1.py` (used by `core/ddp_sub.py`) supports the
   LoRA + LoRA-sub finetuning-from-checkpoint recipe (loading the official
   weights/slidesam_b.pth). The generic `core/ddp.py` + `core/learner5.py`
   path has no LoRA support -- so all CV training must go through the
   ddp_sub-style entrypoint, not core/ddp.py.
4. `datasets/cache_dataset3d.py` is the CACHE WRITER (raw .nii.gz -> 2D
   slice cache: image/*.jpg, label_jpg/*.jpg, meta/*.npy). Its own
   `_get_cached_data` reader is a separate, legacy path expecting a
   different on-disk format (.npz masks under label/) that this project's
   actual cache never uses.
5. `datasets/cache_dataset3d3.py` is the CORRECT reader for what
   cache_dataset3d.py actually writes (jpg-based). Any new "read from cache"
   loader must subclass cache_dataset3d3.Dataset3D, not cache_dataset3d.py's
   class directly (cache_dataset3d_e2.py already does this correctly; the
   new CV loader follows the same pattern).
6. `datasets/eval_dataloader/loader_abstract.py`'s AbstractLoader resolves
   its manifest generically as data_txt_path + dataset_list[i] + "_{split}.txt".
   With dataset_list=['01_BTCV'] and split='test' this would silently
   resolve to the OLD FIXED "01_BTCV_test.txt" (only img0038-40), not a
   given fold's actual 6 held-out volumes. This required a dedicated
   fold-aware eval loader too (see Step 6 below).
7. The `specific_label` config key (present in old configs like
   vit_sub_btcv_bs4.yaml) is NOT consumed anywhere in the actual
   dataset/training pipeline (grepped the whole repo) -- it's a dead/
   vestigial key only referenced in a comment inside a standalone
   visualization script. Intentionally omitted from the new fold configs.
8. Correct BTCV label mapping (verified, important -- an earlier example
   snippet in test/volume_eval_sublora.py used label_idx=2 with a WRONG
   comment "2 = liver"):
       1 = Spleen, 2 = Right Kidney, 3 = Left Kidney,
       6 = Liver,  7 = Stomach
   Paper-aligned 4-organ evaluation set = Liver(6), Stomach(7),
   Left Kidney(3), Spleen(1). Right Kidney(2) is NOT one of the four.

Step 2 -- Mathematically verify the folds
  Script: btcv_cross_validation/scripts/verify_folds.py (re-runnable gate,
  exits non-zero on any failure)
  Checks performed and PASSED:
    2.1 |V| = 30 unique volumes on disk
    2.2 every fold has |Train_k|=24, |Test_k|=6
    2.3 Train_k ∩ Test_k = ∅ for every fold
    2.4 Test_1 ∪ ... ∪ Test_5 = V, |union|=30, pairwise disjoint (each
        volume held out exactly once); Train_k == V \ Test_k for every fold
    2.5 re-running the generator reproduces byte-identical manifests
        (verified via backup + in-place re-run + restore, non-destructive)
    2.6 every manifest volume has a real image+label file on disk, and the
        manifest volume set matches the disk volume set exactly
  Result: ALL CHECKS PASSED.

Step 3 -- Build one shared BTCV cache (all 30 volumes)

Step 4 -- Dedicated BTCV-only CV dataset loader
  NEW FILE: datasets/cache_dataset3d_cv.py
  - Subclasses cache_dataset3d3.Dataset3D (correct jpg-based reader).
  - Reads ONLY 01_BTCV_train_4to1.txt from the fold's data_txt_path --
    never opens or references WORD_50_train.txt.
  - Also reads that fold's 01_BTCV_test_4to1.txt purely as a safety check.
  - Scans the shared cache/all30/ pool, selects only samples whose source
    volume is in that fold's 24 training volumes.
  - HARD-FAILS (raises RuntimeError) if any selected sample's volume is
    also in the held-out set, or if any train volume has zero cached
    samples -- leakage becomes a crash, not a silent bug.
  - Prints a "CV DATASET AUDIT" block (fold path, #train/#held-out volumes,
    #cached samples, #leaked samples, first/last 3 sample paths).
  Smoke-tested against ALL 5 folds (instantiated directly, no training):
    fold1: 24 train / 6 held-out / 7623 cached samples / 0 leaked
    fold2: 24 train / 6 held-out / 7617 cached samples / 0 leaked
    fold3: 24 train / 6 held-out / 8395 cached samples / 0 leaked
    fold4: 24 train / 6 held-out / 7794 cached samples / 0 leaked
    fold5: 24 train / 6 held-out / 8159 cached samples / 0 leaked
  All 5 passed with 0 leaked samples.
